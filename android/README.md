# ProxyTunnel for Android

A real `VpnService` client that routes the whole device through a SOCKS5 proxy you
supply, built so that it can actually run on a phone you own.

```bash
cd android
./scripts/fetch-native-libs.sh          # downloads the tunnel engine, verifies its SHA-256
gradle :app:testDebugUnitTest          # JVM tests, including end-to-end proxy tests
gradle :app:assembleDebug              # app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Then open the app, add a proxy, and press Connect. Android shows its one-time VPN
consent dialog; after that the tunnel comes up.

---

## Why this exists alongside the iOS app

The iOS app is complete and builds, but it cannot tunnel on a device signed with a
free Apple ID. Apple's `com.apple.developer.networking.networkextension`
entitlement — required to run a `NEPacketTunnelProvider` — is issued only to paid
Apple Developer Program members. That is a policy, not a bug, and this project does
not try to work around it.

Android has no such wall:

| | iOS | Android |
|---|---|---|
| Tunnel API | `NEPacketTunnelProvider` | `VpnService` |
| Gate | `com.apple.developer.networking.networkextension` entitlement | none |
| Who can use it | paid Apple Developer Program members | any app, after one user consent dialog |
| Signing | certificate + provisioning profile | a debug key, generated by the SDK |
| Expiry | free-Apple-ID sideloads die after 7 days | none |
| Build machine | macOS (needed for Xcode) | Linux |

So the same product is achievable here end to end: a debug APK on a phone, no
account, no renewal, no Mac.

## What the tunnel actually does

`VpnService.Builder.establish()` returns a `ParcelFileDescriptor` for a tun
interface. Every IP packet the device sends is written to that descriptor. Turning
those packets back into TCP and UDP is the hard part, and there are two ways to do
it:

1. **Write the stack yourself.** That is what the iOS side does: `Packages/ProxyTunnelCore`
   contains a userspace IPv4/IPv6 + TCP implementation in Swift, because a Network
   Extension is handed raw packets and nothing else.
2. **Use a tun2socks engine.** This is the standard Android approach.

This app takes route 2, with **`hev-socks5-tunnel` 2.18.0** (MIT), the engine inside
SocksTun and used by Orbot. It reads the tun descriptor, terminates TCP and UDP, and
forwards through a SOCKS5 proxy, with:

* **UDP relayed through the SOCKS5 association** (`udp: 'udp'`), so QUIC, HTTP/3,
  DNS and games work rather than being silently dropped;
* **remote name resolution** — the proxy resolves names, so the carrier's DNS never
  sees them;
* **fullcone NAT** for the UDP path.

### Why not `xjasonlyu/tun2socks`

It is the better-known project and it was the first choice. Its README lists the
platforms it supports — Linux, macOS, Windows, FreeBSD, OpenBSD — and **Android is
not among them**. Building it for Android would mean maintaining a fork of a Go
program against the NDK. `hev-socks5-tunnel` ships an AAR with `arm64-v8a`,
`armeabi-v7a`, `x86_64` and `x86` already in it.

### Why `minSdk` is 29

Because the AAR says so. Its `AndroidManifest.xml` declares `minSdkVersion 29`, and
the native library is only built for API 29+. The manifest merger rejects anything
lower, so the app targets Android 10 and above. This is a real restriction and it
comes entirely from the engine, not from the app's own code.

## Loop avoidance

If the socket that carries traffic to the proxy were itself routed into the tunnel,
the tunnel could never come up. The fix is one line:

```kotlin
builder.addDisallowedApplication(packageName)
```

That takes this app out of its own tunnel. It is the Android-native equivalent of
the per-IP excluded routes the iOS extension has to install by hand, and it is much
harder to get wrong.

## The password on disk, and what is done about it

This is the one place where Android is *worse* than the iOS implementation, and it
is worth being precise about.

`hev-socks5-tunnel` takes the path of a YAML config file, not a buffer, so the
password has to be written to disk for the duration of the tunnel. On iOS the
password never leaves the Keychain at all.

What the app does about it:

* the config is written into the app's private `filesDir`, which no other app can
  read without root;
* it is written with owner-only permissions;
* it is deleted the moment the tunnel stops, and also on failure paths;
* nothing logs it, and it is never put in an Intent extra or a diagnostic export.

Everything else follows the same rule as iOS: profile metadata lives in JSON, the
password lives in the **Android Keystore** (AES-256-GCM, alias `proxytunnel.secrets.v1`),
and `ProxyProfile` has no field that could hold a secret. There is a unit test that
asserts exactly that, by reflecting over the class's declared fields.

## Choosing a location

The app will not search the internet for proxies, and there is a feature it
deliberately does not have: automatic discovery of "free residential proxies".

That request was declined on technical grounds, and the reasoning is worth keeping
in the repository. Free residential proxy lists are, in practice, one of three
things:

* **open proxies on strangers' machines** — misconfigured servers that someone else
  is paying for, and which it is not yours to route through;
* **honeypots** — endpoints published precisely so that the traffic sent through
  them can be read, logged and rewritten, which is how session cookies and
  credentials get stolen;
* **botnet-adjacent SDKs** — software that pays for the "residential" pool by
  reselling other people's bandwidth from their own devices.

None of those is safe to put a username and password through, and using them is
unauthorised use of someone else's computer.

What the app does instead: you add a proxy you obtained legitimately, label the
country it exits in, and then pick by location. `RegionCatalog` recognises country
names, two-letter codes and common city names in a label like
`ProxyCheap | US | New York`, and the location picker filters and selects from your
own list. It states plainly when you have nothing for a country, instead of
pretending to have found something.

Legitimate sources, in order of how well they work:

* **the provider you already pay for** — most sell SOCKS5 or HTTP endpoints;
* **a paid or trial residential plan** from a vendor whose terms you have read;
* **a free tier from a datacentre-proxy vendor** — datacentre IPs, not residential,
  but legitimate and often free at low volume;
* **your own machine** — Tor's SOCKS port (`127.0.0.1:9050`), `ssh -D 1080 you@vps`,
  or a small VPS running `3proxy`/`dante`.

## Kill switch

Android does this better than an app can, so the app does not reimplement it:

**Settings → Network & internet → VPN → ProxyTunnel → Always-on VPN**, and enable
**Block connections without VPN**.

With both on, nothing leaves the device while the tunnel is down. An app-level
implementation would be weaker, because Android can kill an app but cannot kill the
kernel's routing table on its behalf.

## Tests

`gradle :app:testDebugUnitTest` runs on any JVM — no emulator, no device. The suite
includes:

* byte-level codec tests for SOCKS5 (RFC 1928/1929) and HTTP CONNECT (RFC 9110),
  asserting the exact bytes on the wire;
* validation and redaction tests, including one that fails if a credential ever
  reaches a message or a log line;
* share-link round trips, so a list exported on iOS imports here;
* the location-label tests, including the two-letter-code case that would otherwise
  label "Proxy in Germany" as being in India;
* **end-to-end proxy tests**: a real SOCKS5 server and a real HTTP origin are started
  on loopback inside the test process, the probe performs a real handshake and a real
  relay, and the tests assert on the egress address the origin served. A framing bug
  fails these; a mock would not.

Everything in this repository's test suite is real. There are no tests that assert a
mock was called and call that verification.

## What is verified, and what is not

Verified by CI on every push (see `.github/workflows/build-apk.yml`):

* the Kotlin sources compile against the pinned engine AAR;
* the full JVM test suite passes;
* the AAR's JNI surface is re-checked with `javap` against what this app compiles
  against, so a changed engine fails the build instead of crashing at runtime;
* a debug APK is produced and structurally validated: `classes.dex`, the manifest,
  `BIND_VPN_SERVICE`, `libhev-socks5-tunnel.so` for `arm64-v8a`, `armeabi-v7a` and
  `x86_64`, and a valid debug signature.

**Not verified, and not claimed:**

* that the tunnel carries traffic **on a physical device**. That needs a phone with
  the consent dialog accepted, and there is no device in the build environment. The
  code path is written against the engine's documented JNI contract and the
  pattern `v2rayNG` uses, but "it compiles and the tests pass" is not the same claim
  as "it works on your phone", so it is not made here.
* the HTTP CONNECT and HTTPS CONNECT protocols as *tunnel* upstreams. The engine
  speaks SOCKS5 only; the other two are supported for the connection test and for
  export, and the UI says so on the Connect tab rather than failing obscurely.
